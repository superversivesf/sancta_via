# Sancta Via Devotionals

An offline-first Catholic devotional app built with Flutter, part of the Sancta Via
melos workspace. This app hosts the Today pipeline, guided prayer sessions, and
commitment trackers powered by the shared `sancta_via_devotional_engine` packages.

## Features

### 📖 **Today Pipeline**
- Single daily surface assembling devotional content by day-of-program
- Liturgical-calendar-aware content curation

### 🙏 **Guided Prayer Sessions**
- Step-by-step guided sessions driven by devotional engine programs
- Progress tracking with restart policies and substitution rules

### ⭐ **Commitment Trackers**
- 54-day novena-style tracks with per-anchor completion checkpoints

## Getting Started

This app consumes the shared packages through **path dependencies**, so bootstrap
the workspace once from its root (this links every `sancta_via_*` package and
installs dependencies):

```bash
cd /path/to/sancta_via
melos bootstrap
```

Then run the app from this directory:

```bash
cd sancta_via_devotionals
flutter run                # connected device / simulator
flutter run -d chrome      # web
flutter run -d macos       # macOS
```

The Makefile wraps the common commands:

```bash
make run        # flutter run
make run-web    # flutter run -d chrome
make deps       # flutter pub get
make doctor     # flutter doctor
```

## Content: sources, regeneration, and the launch pipeline

The catalog ships **33 packs** under `assets/content/packs/` plus imported
companion prayers under `assets/content/prayers/`. Three kinds of content exist,
and only the first is copied:

| Kind | Files | Source of truth |
| --- | --- | --- |
| Engine fixtures | the 8 original packs (`angelus`, `divine_mercy_novena`, `five_first_saturdays`, `mercy_hour`, `nine_first_fridays`, `novena_54_day`, `rosary`, `total_consecration`) | `../sancta_via_devotional_engine/test/fixtures/packs/*.json` — committed here **byte-for-byte** |
| App-authored packs | 6 routine, 9 novena, and 10 chaplet/litany packs | authored in this app's `assets/content/packs/` |
| Imported prayers | `assets/content/prayers/*.json` | generated by `tool/import_prayers.dart` from the prayer companion's assets |

### Regeneration order (when a content source changes)

1. **Engine fixtures → wrapper embed** (the in-memory repository's catalog):

   ```bash
   cd ../sancta_via_devotional_engine_riverpod
   dart tool/embed_packs.dart
   ```

   The tool validates the whole fixture directory through the engine's own
   loader before writing `lib/src/embedded_packs.dart`. Do not hand-edit that
   file; `test/embedded_packs_test.dart` pins it byte-for-byte against the
   fixtures.

2. **Engine fixtures → app assets** (byte-for-byte copies):

   ```bash
   # from sancta_via_devotionals/
   cp ../sancta_via_devotional_engine/test/fixtures/packs/*.json \
      assets/content/packs/
   ```

   Only the eight engine-fixture packs live in that source directory; the
   app-authored packs are unaffected. `test/services/content_app_asset_pin_test.dart`
   pins the copies' byte equality and the pubspec asset declaration.

3. **Companion prayers → imported PrayerText JSON**:

   ```bash
   # from sancta_via_devotionals/
   dart run tool/import_prayers.dart
   ```

   Reads the prayer companion's assets read-only, maps them onto the engine's
   `PrayerText` shape, drops (and prints) entries without a usable
   source/license, and rewrites `assets/content/prayers/` idempotently.
   `test/content/routine_packs_test.dart` pins the accepted/rejected split.

4. Re-run the touched suites:

   ```bash
   flutter test
   flutter analyze
   ```

`make import-prayers` and `make embed-packs` call steps 3 and 1 for you.

### The launch content pipeline

No manual step is needed to ship content: on first launch (and whenever the
bundle's computed content version changes) the app parses every declared
`assets/content/packs/*.json` through the engine's `PackLoader` and seeds the
SQLite catalog (`lib/services/content_asset_service.dart`,
`contentLoadedProvider` in `lib/providers/content_providers.dart`). The content
version is a sha256 over the pack ids and asset byte digests, so any pack edit,
addition, or removal triggers a one-shot re-seed. Enrollment-derived schedules
(e.g. a novena's user-picked start date) are re-applied after a re-seed, so user
state is never regressed.

## Deferred content work (ledger)

Two content features are deliberately NOT implemented; they are ledgered here
rather than faked in the app:

- **Lectio Divina readings.** The `lectio_divina` routine pack ships its
  authored prayer text, but the reading-per-day feature (selecting and
  rendering scripture for the day) is deferred content work. The
  `bible_data` / `bible_data_riverpod` path dependencies stay in place for it;
  no screen reads them yet.
- **Promises and indulgence notes.** The packs carry no per-devotion promise
  or indulgence text. Authoring that content — with the sources/licenses the
  engine's `PrayerText` shape requires — is deferred; the app must not invent
  or paraphrase it. (The Progress tab's indulgence explainer is generic and
  source-attributed separately.)

## Architecture

- `lib/main.dart` — application entry point (root `ProviderScope` →
  `MaterialApp.router`); owns the notification tap listener and app-open
  refresh, and the onboarding gate.
- `lib/config/routes.dart` — GoRouter configuration (`today` route at `/`)
- `lib/screens/` — feature screens (Today, onboarding, enrollment, practice,
  session player, progress, settings)
- `lib/providers/` — Riverpod state: content pipeline, Today assembly,
  settings, progress, session player
- `lib/services/` — content assets, enrollment, progress, substitution, grace
  windows, notification planning/wiring
- `lib/repositories/` — the SQLite program repository (packs, enrollments,
  progress, notification index)
- Path dependencies link the shared Sancta Via engine/UI/data packages
- Database layer uses `sqflite` with `flutter_local_notifications` + `timezone`
  for scheduled reminders

### Startup order

The dependency order is **db → content → notifications → router**: the
app-open hook awaits the content migration (which opens the database and seeds
the catalog) before the planner reads packs, enrollments, and progress. The
router is constructed before `runApp` by necessity but consumes none of that
state; the notification tap listener is attached before initialization so the
cold-start launch payload is never dropped (see the comment at the top of
`lib/main.dart`).
